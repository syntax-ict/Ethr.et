# Security Policy

ETHR stores employee records, bank details, salary history and scanned identity
documents for multiple tenant organizations. Report anything that could expose
one tenant's data to another, or to the public.

Do **not** open a public issue for a security report.

Include where you can: what you did, what happened, what you expected, and
whether you needed an authenticated session or a second tenant to reproduce it.
A tenant-isolation report is far more actionable with the two subdomains named.

Please do not run automated scanners against a production host without asking
first, and do not access, modify or retain another tenant's data beyond the
minimum needed to demonstrate the finding.

## Scope

In scope: the Laravel API (`api/`), the Next.js frontend (`src/`), the
deployment and operational scripts (`scripts/`, `docker/`, `infrastructure/`),
and any running ETHR instance the reporter is authorised to test.

Out of scope: findings in third-party dependencies that are already public and
have no ETHR-specific exploit path; missing headers or configuration on a host
that is explicitly a development environment; and reports generated by a scanner
with no demonstrated impact.

## What we treat as most serious

Ranked by what would hurt this product most, not by generic severity:

1. **Cross-tenant data access** — any path by which one tenant reads, writes or
   infers another's data. Tenant isolation is enforced by the `BelongsToTenant`
   global scope, which is fail-closed (no tenant context yields no rows). Every
   `withoutGlobalScope` bypass must re-apply a tenant predicate; a missed one is
   a P0. See `tests/Feature/Security/` for the shape these take.
2. **Authentication and session handling** — Sanctum session fixation, MFA
   bypass, password-reset or OTP flaws, impersonation escape.
3. **Exposure of `.env`, `storage/`, `.git/` or backups** through the web root.
4. **Audit-log tampering** — `audit_log` is append-only, enforced by database
   triggers. Any way to update or delete a row is in scope.
5. **Employee document access** — uploads are stored outside the document root
   under a per-tenant prefix and served through signed, authorised URLs. A path
   that returns a document without authorisation is in scope.
6. **Payroll correctness with a security consequence** — for example, altering
   another user's salary or tax outcome.

## What this policy does not claim

This file describes where to send a report and what we consider serious. It is
not an assertion that the controls above are complete or verified.

`docs/SECURITY.md` is a different document: it records the internal security
*posture*, including known gaps. `docs/audit/BASELINE.md` lists the open risks
measured against the code, and `docs/HOSTING_VERIFICATION_CHECKLIST.md` records
which production-hosting controls are still `NOT VERIFIED`. Read those before
assuming any control here is in place.
