# E2E specification 03: sign-in, tenancy and access control

Columns, personas and modes are defined in the [README](README.md#how-a-test-case-is-written) and the
[test plan](01-TEST-PLAN.md#5-test-accounts-and-personas). API paths are under `/api/v1`. Error
responses are `application/problem+json` with `type`, `title`, `status`, `detail` and, for 422,
`errors`.

**Before running the negative sign-in cases**, read the lockout rule (AUTH-010): five failures in a
minute on one identifier, organisation and IP give 429; ten in fifteen minutes lock it for fifteen
minutes. Wrong authenticator codes (MFA-012) and wrong sign-in codes (AUTH-038) have their own
fifteen-minute locks, counted per account. Use a spare account (EMP3) for them, and run them last.

**Third edition (2026-11-08).** Cases were added for #478, #486, #488, #490, #492, #561, #623,
#625, #632, #635, #638, #640 and the sign-in, role and billing items of the A-Z review train #624,
and PLAN-014 to PLAN-018 were rewritten for the console feature controls (#464, #480, #636).
Priorities were re-tiered: **P1** is kept for sign-in for each role, a second factor that cannot be
skipped, cross-organisation or cross-department exposure, refusals that protect data or money, and
the one happy path of each section's main flow. Enumeration-resistant wording, rate-limit counts
(09 owns the numbers), expiry timings and audit wording are P2.

**Since the third edition (2026-11-09).** Cases were added or changed for one live login per
employee and no second admin at one's own level (#670, #678: ACC-020, ACC-031), writes that name no
organisation (#668: TEN-027), the address while impersonating (#680: IMP-004, IMP-008) and upgrades
billed for the rest of the period (#670: PLAN-022).

**Org-type-aware configuration (#682).** Sign-up asks the kind of organisation in law, grouped by
sector (section 6a, ORG-009 to ORG-011). What the kind decides is file 07's section 13; the setup
wizard's answers are file 04's section 1a. TEN-014 notes where the fiscal year now lives. The
platform console gains no screen for the kinds: the catalogue is written by migrations.

## 5b. Invitations sent from the queue

Since #458, an invitation for many people at once (an import with logins, "Resend to everyone not
activated", the device migration's "Send invitations", the daily reminders) is not sent in the request.
Each one is a row in `invitation_sends` and a queued job, spaced at **30 a minute per organisation**
for email (10 for texts). There is no worker: the outside callers drain the queue every 5 minutes, so
a small batch reaches inboxes within about 5 to 10 minutes. **One person's invitation (Add employee,
Invite user, Resend) is still sent at once.** `POST /users/invitations` and
`GET /users/invitations/{batch}` need `users.invite` (`hr_admin`, `tenant_admin`).

**Text invitations are off** (owner decision 2026-10-28, console switch CON-P-023), so a person with a
phone and no email is activated in person. **The bulk resend emails every `invited` login in the
organisation:** run these cases on QA Audit only, and first check that Settings → Users → "Not
activated" holds only addresses the team controls.

## 11. Plans, limits, features and billing

Run on the QA Isolation organisation. PA changes its plan, status and feature exceptions on
request. A **trial** organisation has every plan feature and no limits, so the plan cases need it
out of trial.

A feature's availability is decided by one gate (`Services/Features/FeatureGate`, #460), in order:
switched off by the platform, revoked for this organisation, granted to it, outside a restricted
rollout, then the plan. Since #464 the console sets the platform state of every feature and one
organisation's grant or revoke, with a reason and an optional end date; since #480 integrations and
public pages are switches too; since #636 every switch offered works, and attendance, leave,
employee management and notifications are core and cannot be switched. **The console screens are
file 08's (CON-P cases); this section is what the organisation sees.** A platform switch changes
every real customer at once: never set one for a test without the owner's go-ahead, and use a
revoke or grant on QA Isolation instead.
